# 维护说明（流程外提示词）

> 给维护这套机制的人——首先是你，AI。改任何文件之前先读这一份；改完按第 5 节验，四步之外不算验过。

## 1 意图

这里是"同一类任务的整套做法"：一条一份正文，人复制它给 AI，开工。

它**不挂载、不参与拼装、与流程零关系**——不进 `flow.json`，不被任何流程引用，流程也看不见它。所以：改它不会影响任何流程；反过来，流程坏了也不该影响它。

每条方案是人与不同 AI 协作时的共同参考件：把合作意图、角色分工、重要边界和可用方法放在同一处，让不同经验水平的接收方不必只靠临时口述理解任务。它争取守住合作方式的起点，不保证实际结果质量；方案供参考，用户最新表达和当前实际情况优先。

### 什么值得收录

新增前先回答：

1. 同类合作任务是否会重复出现？
2. 它是否需要双方共同理解一种合作方式，而不只是传递一项事实或一句命令？
3. 它是否有相对完整的意图、角色或边界，使不同 AI 能据此开展同类合作？
4. 去掉项目、人物、数据和一次性偏好后，是否仍有值得跨主题、跨会话复用的内容？

回答不清楚就先讨论，不为了凑条目而新建。

### 什么不应收录

- 某个项目的一次性事实、临时决定或具体业务材料；
- 只想让 AI 执行一次的指令；
- 没有完整合作意图的零散句子或收藏片段；
- 必须绑定 `flow.json` 动作和轮次才有意义的流程块；
- 强迫 AI 不顾情境执行固定步骤、固定配额或固定产物的操作脚本；
- 与已有条目只有措辞差别、没有新合作意图的重复方案。

### 正文与细则怎么分工

正文写合作意图、双方分工、适用边界、诚实要求和灵活使用原则。细则只在某类内容需要独立展开时存在，例如方法库、产物规范、质量判据或长示例；细则数量由实际责任决定，不设数量目标。

正文和细则都不写固定节拍、确认仪式、每轮仪式性输出或方法使用配额。每句话都应影响 AI 遇到具体情况时的判断；只是显得完整、删了也不影响判断的内容不写。方案不能压过用户当前明确表达，也不能把 AI 的主动理解成接管用户主导权。

### 两种形成入口

- **从实践沉淀**：真实任务中已经形成并验证的方法，通过「沉淀」动作读取案例、提出候选并由用户取舍。证据提炼步骤见 `promptflow/data/skeleton/briefs/settle_prefab.txt`；进入资产设计后，统一以本说明为准。
- **直接设计**：合作意图已经明确，但尚未有实践案例。直接讨论任务定位、角色、边界和方法，再按本说明完成收录判断、设计和验收；不要求先制造实践证据，也不强制使用「沉淀」动作。

两种入口只表示证据来源不同，不代表资产有两套标准。是否正式写入或修改资产，均需用户明确指令。

### 新增还是更新

新增前读取 `data/` 现有条目，比较任务定位、适用范围和方法重叠程度：只是补充或修正既有方法时，提出更新原资产的草案；确实属于不同任务或独立方法时才新建；无法判断是否同主题时交由用户决定，不擅自覆盖或另建。

### 现有条目说明结构如何变化

| 条目 | 为什么采用当前结构 | 不能据此推断什么 |
|---|---|---|
| 报告 | 有骨架、结论清单、成对版本和正式成品责任，因此需要多份产物与质量细则 | 不是所有方案都要多份细则和固定产物 |
| 探索 | 改善当下认识，没有必须交付的产物，因此正文＋一份方法细则即可 | 不是所有方案都只能有一份细则 |

这些条目只说明“结构随业务责任变化”，不是后续方案必须二选一的模板。

### 结构验收与使用效果

`CheckOffflow` 只能证明文件、引用和复制生成符合结构，不证明合作有效。入库前还应脱离撰写者位置，从第一次收到方案的接收方视角检查：它可能怎样理解意图和改变行为，是否存在过度约束、案例污染、歧义或只能猜测的信息缺口，正文与细则是否可执行。这个检查只是自我风险预判，不代表独立评审或真实使用效果；真实使用中的问题继续回到对应资产修正。

## 2 形式

```
app/modules/offflow/
├─ definition/   OffflowPrompt.ahk / OffflowReference.ahk   模型
├─ repository/   OffflowRepository.ahk                        读取与真实路径（只碰文件）
├─ action/       OffflowPromptReferenceCopy.ahk               方案引用生成与复制
├─ validation/   OffflowValidator.ahk                         判定（只判对错）
├─ docs/         维护说明.md
└─ data/
   ├─ prompt_reference_copy.txt                               公共方案引用提示词，不是条目
   └─ <key>/
      ├─ meta.json      { name, purpose, category, hidden }
      ├─ body.txt       正文，一份
      └─ references/<id>/{meta.json, body.md}
```

`meta.json` 字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 界面显示名 |
| `purpose` | 是 | 这套做法解决什么任务 |
| `category` | 否 | 分类标签，只用于筛选与分组；自由文本，≤12 字；不写＝未分类 |
| `hidden` | 否 | `true` 默认不进取用面板，可直接查看数据或临时切换为可见；取值 `true`／`false`（`1`／`0` 等价），不写＝可见 |

**`hidden` 影响什么**

- 只决定**取用面板列不列它**；不影响文件、不影响复制、不影响校验。隐藏条目可直接查看数据目录，或临时改为 `false` 后在取用面板检查。
- 不写＝可见；写了就按值算。
- 判断路径：数据目录里存在、取用面板没有 → 先查它的 `meta.json` 里 `hidden`。
- `sample` 为什么是 `true`：见第 3 节（它是参照件，不是可直接粘贴的成品）。
- 解除：把 `true` 改成 `false`（或删掉该字段）。

两条硬规则：

1. 正文里的 `{{ref:id}}` **在复制正文时**换成细则文件的绝对路径；找不到 id 直接报错。
2. 细则（`body.md`）里**不许再写 `{{ref:}}`**——渲染只发生一次，写了就是死字。

### 复制正文与复制引用

- **复制正文**：复制 `RenderBody` 的结果，适用于无法读取本地文件的 AI；面板预览与这个出口共用同一份正文。
- **复制引用**：复制 `OffflowPromptReferenceCopy.Build(key)` 的结果，适用于能读取本地文件的 AI。文案只含名称、用途、正文绝对路径和细则定位规则，不包含正文全文。
- 两种复制都表达合作意图：方案供 AI 参考，不是必须机械执行的流程；用户最新表达和当前实际情况优先。

公共引用提示词在 `data/prompt_reference_copy.txt`，由 `OffflowPromptReferenceCopy` 读取，不在面板或类里另写一份。模板只支持 `{{name}}`、`{{purpose}}`、`{{bodyPath}}`、`{{referencesPath}}` 四个字段；`{{ref:id}}` 是交给 AI 的原文标记，必须保留，不参与字段替换。复制结果通过 `referencesPath` 指向真实的 `references/<id>/body.md`。

这个 `.txt` 直接位于 `data/` 根目录，不是方案条目：不给它建 `meta.json`，不移入某个方案目录，条目列表和条数都不包含它。不生成带绝对路径的镜像正文。

## 3 怎么新增一条

1. 先按第 1 节判断值得收录、需要新增还是更新，并写清合作意图、分工和必要边界。
2. 在 `data/` 下建目录，**目录名用英文**（key）；中文名写进 `meta.json` 的 `name`。
3. 照 `data/sample/` 的形状抄结构：`meta.json`（`name`／`purpose`／`category`／`hidden`）＋ `body.txt` ＋ 按需的 `references/<id>/{meta.json, body.md}`。
4. 正文里用 `{{ref:id}}` 指细则；细则里不写它。
5. 跑 `CheckOffflow`：报告 `OK`，再打开 `offlow-prompts/<key>.txt` 确认成品干净，并在真实面板检查正文预览、复制正文和复制引用。

`data/sample/` 是这套形状的**参照件**：结构与任何一条完全相同，只是 `hidden: true`（不进取用面板）。学它的构成，不抄它的内容。

## 4 校验指令的执行规则

```powershell
# 有控制台
app\cli\CheckOffflow.bat [输出目录]

# 无控制台调用（AI 常用）
Start-Process -FilePath "app\cli\CheckOffflow.bat" -ArgumentList '<输出目录>' -WindowStyle Hidden -Wait
```

- 产物分两类：
  - `<输出目录>\offlow-check.txt`：**报告**，只有结论与条目索引；
  - `<输出目录>\offlow-prompts\<key>.txt`：**成品**，内容就是取用时复制到剪贴板的那段——一个字节不加（无标题、无额外换行、UTF-8 无 BOM）。
- 报告通过时：`OK`／`条数：N`／`成品：<目录>`／`条目：a、b`。
- 失败时第一行 `失败 N 条`，随后逐行 `条目 / 文件 / 问题`。
- 每次运行先清空 `offlow-prompts\` 下的旧成品，但**只在确认该目录是本工具创建时才清**：目录里有归属标记 `.offlow-prompts` 才清 `*.txt`（不递归、不删子目录、不删目录）；没有标记就一个文件都不删，报告里写 `成品目录已存在且非本工具创建，未做清空` 并以失败退出，本次也不写成品。
- **成品与渲染的一致性由脚本自己断言**：写完立即读回、与内存结果比对，不等即报 `成品与渲染不一致：<key>`。换行基准 LF。
- **只看产物文件**：stdout 与退出码都不可信（好文件坏文件退出码可能都是 0）。
- 脚本自身出错（语法、找不到 AutoHotkey、60 秒超时）也写同一个报告文件，内容以 `脚本异常` 或 `超时` 开头——"没有报告"只剩一种可能：输出目录不可写，此时退回系统临时目录。

## 5 改完之后怎么验

1. 改正文、细则、`meta.json` 或公共引用提示词；
2. 跑一次 `CheckOffflow.bat`；
3. 打开 `offflow-check.txt`，确认 `OK`；不 OK 就按行改；
4. 打开 `offlow-prompts\<key>.txt`：它应当**就是**复制正文时取用的内容——没有残留 `{{ref:`，路径都真实存在，且没有任何标题或多余空行。

四步之外不算验过。第 4 步最关键：校验器只能证明引用**指向存在**；成品与"复制正文的内容"是否同一段字，由脚本的断言担保，人只需确认文件本身干净。自检还会对每条有效方案实际调用 `Build(key)`；公共模板缺失、为空或含未知字段都会失败。复制引用仍需在真实面板验证按钮、剪贴板和路径读取。

## 6 校验器判断什么

1. `meta.json` 存在，`name`／`purpose` 非空，`hidden` 为 true/false，`category`（若写）非空且 ≤12 字，`key`（若写）与目录名一致；
2. `body.txt` 存在且非空；
3. 每个 `{{ref:id}}` 都能落到一份存在的细则；
4. 细则 `body.md` 内不出现 `{{ref:}}`；
5. 细则目录存在 `body.md`；
6. 公共引用提示词存在且非空；
7. 每条通过数据校验的方案都能由 `OffflowPromptReferenceCopy.Build(key)` 生成引用文案，未知字段会报错。

## 7 已知边界

- 单条无数量上限校验（人工控制）。
- 校验器不检查正文的**表达质量**，只查结构。
- 没有独立命令行复制入口：复制由取用面板或手工完成。
- 升级前生成过的成品目录没有归属标记，会被拒绝一次（不删任何文件）；换输出目录，或人工确认后放入一份 `.offlow-prompts` 再跑。
