# 演示导读

## 为什么有这份文件

你是 AI。读这份东西的目的只有一个：**在一个已有主题里，判断此刻该用哪个动作、该读哪些文件、产出写去哪。**

没有它的时候，你拿到一个主题目录，只看到 `需求.txt` 和几份 `vN.md`，不知道九个动作各自在什么场景被触发、哪个动作会带上哪些文件——只能等人在对话里临时举例。成本全落在人身上。

有了它，你能顺着"场景 → 动作 → 输入 → 产物"自己判断。边界：它是导读，不替代设计文档（讲为什么这么设计），也不替代 `demo` 本身（真跑过的现场）。

## 1 最小阅读路径

按这个顺序读七份，够了。这一列写的是**角色与上下游**，换任何主题都不变：

| 顺序 | 文件 | 读完知道什么（角色＋上下游） |
|---|---|---|
| 1 | `demo/需求.txt` | **起点角色**：人的业务输入。上游没有人，下游交给 AI 出第一版回应；AI 只读不改它 |
| 2 | `demo/v2.md` | **中间产物角色**：AI 的一轮回应。上游是人的回复，下游是下一轮讨论；版本只增，新的一版取代旧的成为当前有效 |
| 3 | `demo/实施文档.md` | **收口角色**：讨论与执行之间的翻译层。上游是讨论收敛，下游所有执行只认它 |
| 4 | `demo/已实施.md` | **回执角色**：执行或拆分的结果报告。上游是定稿／步骤拆分，下游回母主题做验收与统计 |
| 5 | `demo/实施步骤/02-答辩形态/02-答辩形态.md` | **递归子主题入口**：由母主题"步目"拆出生，目录里是它自己的需求＋版本链，独立跑一轮；**同一结构可再往下嵌**——步骤里还能有步骤、也能有微调，这就是递归 |
| 6 | `demo/结果微调/01/需求.txt` | **立案角色**：执行后发现的独立问题单开一格，不打断主线；内部复用整条主线（需求→版本链→实施文档），结果回母主题记账 |
| 7 | `demo/.aiprocess/log.jsonl` | **证据角色**：每轮一行——`action` 哪个动作、`properties` 输入与产物路径、`content` **整份提示词原文**。上游是脚本复制提示词时写入，下游是你分析"AI 当时看到什么"的唯一凭证；同目录 `flow.txt` 定这套主题用哪套流程，`stats.json`／`统计.md` 是它的汇总 |

三层同构、可互相嵌套：**主线（根）→ 步骤（步目拆出）→ 微调（执行后立案）**；步骤里还能再拆步骤、再开微调，层数不设限，每层都跑同一套动作。递归不是额外机制，是这三层用的是同一套结构。

其余文件按需展开。`v1.md` 是被 `v2.md` 取代的草稿，除非要追溯，不必读。

## 2 结构

主题是一个目录，不是一个文件。四层：

```
<主题>/
├─ 需求.txt              人写，起点
├─ vN.md                 AI 写，每轮一版，N 只增
├─ 对vN的回复.txt          人写，对 vN 的作答
├─ 实施文档.md            AI 写，定稿（复回复·实 的产物）
├─ 已实施.md              AI 写，拆分或执行的结果
├─ 实施步骤/NN-xxx/      每步是独立对话域：需求 → vN → 回复（+ 同名步骤说明）
├─ 结果微调/NN/          执行后发现的独立问题，内部复用主线结构
└─ .aiprocess/          脚本写，不要手改
```

`.aiprocess/` 四件：

| 文件 | 是什么 |
|---|---|
| `flow.txt` | 这个主题用哪套流程（一行 key） |
| `log.jsonl` | 每轮一行：`action`、`properties`、`content`（**当轮整份提示词**） |
| `stats.json` | 轮次与时长统计的原始数据 |
| `统计.md` | 由上面三份生成的人读版：讨论／执行／重建轮次、文件数、字符数。两个读法：**"重建轮"就是复关系那一轮**；它的"文件数"只算内容文件，不含 `.aiprocess` 四件套，别拿去和目录里的总文件数对 |

## 3 动作×输入×产物

九个组合，只有九行。**"带进来的文件"决定这一轮你能看到什么**，没列出的文件你只能自己决定读不读。

| 组合 | 带进来的文件 | 产物 |
|---|---|---|
| 复需求·single | `需求.txt` | 首版 `vN.md` |
| 复回复·direct | `对vN的回复.txt` | 下一版 `v(N+1).md` |
| 复回复·实 | `对vN的回复.txt` | `实施文档.md` |
| 质检码·single | 不点名（"对本次产出"） | `v(N+1).md`（清单） |
| 复盘·答辩 | 不点名（"当前主题的全部上下文"） | `v(N+1).md`（题） |
| 复盘·技炼 | 同上 | `v(N+1).md`（题） |
| 复执行·改吧 | 不点名 | `已实施.md` 或 `v(N+1).md` |
| 复执行·步目 | 实施文档／最新回复／最新版本，三档取一 | `实施步骤/` ＋ `已实施.md` |
| 复关系·auto | 整个主题目录（含约定之外的非标准文件） | **无文件** |

"不点名"的四行是真实设计，不是遗漏：那些动作只带一句指令，靠会话上下文干活。要不要补文件，是这套流程已知的边界，不在你这一轮擅自决定。

## 4 怎么分析一个块的效果

被人问"某个块有没有起作用"时，按五步走，不要凭印象说话：

1. **定位**：查该流程 `flow.json` 的 `recipes`，看这个块挂在哪个组合（`动作|策略`）；
2. **取提示词**：到对应层的 `.aiprocess/log.jsonl` 里按 `action` 找当轮记录，读 `content` 字段——那里存着整份提示词。本 demo 的体量可供判断：复需求 717 字、复回复 602／733 字、复执行 706 字、复关系 2381 字；
3. **取输入**：按第 3 节那张表，读这一轮带进来的文件；
4. **取产物**：读这一轮写出的文件；
5. **判断**：在产物里找块原文某句话留下的、可指认的痕迹。

两条边界，写分析时必须带上：

- 找不到痕迹，只能说"没被响应"，不能说"没用"——**被响应 ≠ 有用**；
- 单个样本没有对照。要证明有用，得让同一个动作去掉该块再跑一轮；本 demo 没有对照组，这是已知局限。

## 5 无产物动作

数文件会漏掉它们。`复关系` 不写任何文件，只有根目录 `log.jsonl` 里一条记录（本 demo 一条，`content` 2381 字）。同理 `流程归属`、`完成通知` 也只进日志。要确认某个动作跑过，按 `action` 字段查日志，不要按文件数。
